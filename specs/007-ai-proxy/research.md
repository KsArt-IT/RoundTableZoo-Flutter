# Research — 007-ai-proxy

**Feature**: [spec.md](./spec.md) | **Дата**: 2026-08-22

**Обновлено 2026-08-22** под `backend-proxy.md` **v0.3**: R6, R7, R15, R16 переписаны по
результатам живых прогонов Gemini (модель, настройки, схема ответа, якоря), добавлены R19–R21.

Решения Phase 0. Источники истины: `project/architecture/backend-proxy.md` (серверная схема),
`specs/004-table-screen/contracts/ai-proxy-client.md` (клиентский контракт), конституция.

Каждый пункт: Decision → Rationale → Alternatives considered.

---

## R1. Где живёт исходный код службы

**Decision**: новая папка `proxy/` в корне репозитория, рядом с `app/` — самостоятельный
TypeScript-проект со своим `package.json`, не подпапка `app/`.

**Rationale**: у службы свой рантайм, свой менеджер пакетов и свой цикл развёртывания; вложить её в
`app/` значило бы, что `flutter analyze`/`flutter test` и `dart run build_runner` начинают видеть
чужие файлы. Корневая папка соответствует уже сложившейся раскладке репозитория (`app/`,
`project/`, `specs/`, `tools/`), где верхний уровень — это «разные виды артефактов». Карту
репозитория в `CLAUDE.md` нужно дополнить строкой про `proxy/` — это часть задачи, а не побочный
эффект.

**Alternatives considered**: отдельный репозиторий — отвергнут: спека, контракт и клиент правятся
одним изменением, разносить их по репозиториям для соло-проекта означает рассинхрон контракта.
`app/proxy/` — отвергнут по причине выше.

## R2. Язык и инструментарий службы

**Decision**: TypeScript + Wrangler (`wrangler.toml`, `wrangler dev`, `wrangler deploy`), тесты —
Vitest с пулом `@cloudflare/vitest-pool-workers`, который поднимает настоящий рантайм Workers с
эмулированными D1 и KV.

**Rationale**: контракт `/react` — это разбор и валидация JSON в пяти местах (вход, конфиг, ответ
Google, ответ Gemini, выход), типы ловят ровно тот класс ошибок, из-за которого клиент получил бы
`invalid_response`. Пул vitest для Workers даёт настоящие привязки D1/KV в тестах, поэтому
атомарность счётчиков (R8) проверяется на реальном SQLite, а не на моке.

**Alternatives considered**: чистый JavaScript — отвергнут: валидация контракта без типов
превращается в ручные проверки в рантайме. Mock-обёртки вместо `vitest-pool-workers` — отвергнуты:
главное, что нужно проверить (гонка на инкременте), на моках непроверяемо по построению.

## R3. Как клиент получает подтверждение подлинности

**Decision**: собственный `MethodChannel` к Android Play Integrity (`com.google.android.play:integrity`),
обёрнутый в `core/integrity/integrity_token_provider.dart`. Стороннего Flutter-пакета не
подключаем.

**Rationale**: нужен ровно один вызов платформы («дай токен»), это ~40 строк Kotlin в
`MainActivity`-соседе. Класть критичный для безопасности путь в зависимость от стороннего пакета,
который может перестать обновляться вместе с Play-библиотекой, — плохой размен для одного метода.
В проекте уже есть прецедент обёрток платформенных механизмов в `core/` (`notifications/`,
`sharing/`), раскладка не новая.

**Alternatives considered**: pub-пакет-обёртка над Play Integrity — отвергнут: экономит десятки
строк ценой зависимости на пути, который при протухании ломает AI целиком; проверить актуальность и
состояние сопровождения такого пакета можно только онлайн, а решение нужно принимать сейчас.

## R4. Standard API и переиспользование одного токена

**Decision**: Standard-запрос Play Integrity: подготовка провайдера токенов один раз (лениво, при
первой надобности), затем один запрос токена, который кэшируется на весь процесс (Clarifications
Q2). `requestHash` не используется для привязки к конкретному запросу.

**Rationale**: решение пользователя — один токен на запуск. Standard API это позволяет; классический
запрос с nonce на каждый вызов упирался бы в квоты Google и в собственный бюджет времени ответа.

**Сознательный размен, который нужно назвать честно**: раз токен не привязан к телу конкретного
запроса, он не защищает от переигрывания перехваченного токена в пределах его срока жизни. Защита,
которую он реально даёт и которой требует `backend-proxy.md` §5, — «запрос пришёл из настоящей
установки настоящего приложения», а не «этот конкретный запрос не переигран». Персональный
суточный лимит по `installId` ограничивает ущерб от такого переигрывания сверху. Компенсирующий
механизм на клиенте — FR-010a: отклонённый службой токен один раз обновляется и запрос
повторяется, поэтому долгоживущий процесс не ломается навсегда, когда токен всё-таки протухнет на
стороне Google.

**Alternatives considered**: свежий токен на каждый запрос (вариант C вопроса Q2) — отвергнут
пользователем; технически он снял бы размен выше ценой квоты и задержки. Кэш с TTL 15 минут
(вариант B) — отвергнут пользователем.

## R5. Как служба авторизуется в Google

**Decision**: подпись JWT алгоритмом RS256 средствами Web Crypto (`crypto.subtle.importKey('pkcs8')`
→ `sign('RSASSA-PKCS1-v1_5')`), обмен на access token у `oauth2.googleapis.com/token`, токен
кэшируется в KV под ключом `gcp:token` с TTL 50 минут при часе жизни.

**Rationale**: дословно `backend-proxy.md` §5.1. Кэш даёт два эффекта: ~29 записей в KV в сутки
вместо одной на запрос (лимит бесплатного тарифа — 1000 записей/сутки) и RSA-подпись раз в 50 минут
вместо каждого вызова, то есть единственная заметная CPU-операция не приближается к пределу 10 мс
CPU.

**Alternatives considered**: клиентские библиотеки Google — отвергнуты: рассчитаны на Node с его
модулями, в рантайме Workers не работают. Хранить долгоживущий токен в переменной модуля — отвергнуто:
изоляты Workers живут непредсказуемо, кэш в KV общий для всех изолятов.

## R6. Вызов Gemini: модель, настройки, разбор

**Decision**: `POST generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`.
Основная модель — `gemini-3.5-flash-lite`, резервная — `gemini-3.1-flash-lite`; **точные версии, без
алиасов `*-latest`**. Список моделей по приоритету лежит в KV-конфиге, не в коде. Обязательные
настройки запроса: `thinkingConfig.thinkingLevel = "minimal"`, `responseMimeType =
"application/json"`, явная `responseSchema` из трёх полей (`mood`, `reply`, `intensity`).
`temperature` **не задаётся**.

**Rationale** (всё подтверждено живыми прогонами 2026-08-22, `backend-proxy.md` §4.1, проба —
`project/experiments/gemini_prompt_probe.sh`):

- Выбор lite-моделей продиктован квотой, не качеством: у обычных Flash суточный лимит бесплатного
  тарифа — 20 запросов, это нерабочая цифра.
- `thinkingLevel: minimal` обязателен: у не-lite моделей 3.x «размышления» включены по умолчанию на
  уровне `medium` — лишние токены и лишняя секунда на реплику в 200 символов. Проверка, что
  подействовало: в `usageMetadata` ответа нет `thoughtsTokenCount`.
- `temperature` не трогаем: дефолт 1.0, а значения ниже, по прямому предупреждению Google, дают
  зацикливания. Разнообразие обеспечивают якоря (R15), а не температура.
- Алиас `*-latest` переезжает на другую модель без предупреждения — промпт начал бы вести себя иначе
  без единого коммита с нашей стороны.
- `character` в схеме **отсутствует**: служба знает `characterId` из запроса, спрашивать его у
  модели — лишние токены и лишний режим отказа.
- `enum` у `mood` обязателен и должен совпадать с `ReactionTone` клиента буква в букву. Без него
  модель возвращает выдуманные значения (`annoyed`, `supportive`) и даже кладёт туда оценку
  пользователя (`"2"`). Опасность в том, что `ReactionTone.fromStorage` молча превращает неизвестное
  значение в `neutral` — поле деградирует беззвучно, и в логах ничего не видно.
- `description` у `mood` тоже обязателен: именно он разводит «тон моей реплики» и «оценка
  пользователя 1–5».
- `minimum`/`maximum` у `intensity` работают, но это подсказка модели, а не гарантия рантайма: до их
  появления модели дважды возвращали `2`. **Кламп и проверка на `NaN` на службе обязательны** — это
  внешний вход, а не свой код.

**Разбор ответа**: полезная нагрузка — строка в `candidates[0].content.parts[0].text`, её нужно
разобрать как JSON. Рядом с `text` в `parts[0]` лежит `thoughtSignature`, поэтому брать надо именно
поле `.text`, а не «первое поле объекта». `finishReason` обязан быть `STOP`; `MAX_TOKENS` означает
обрезанный JSON — это и есть случай для одного повтора и последующего `422`.

**Alternatives considered**: обычные Flash-модели — отвергнуты квотой (20 запросов в сутки).
Round-robin по двум моделям — отвергнут: модели пишут по-разному, и при чередовании манера персонажа
скачет через реплику; при строгом приоритете расхождение видит только тот, кто добрался до хвоста
квоты. Имя модели в коде — отвергнуто: смена модели не должна требовать развёртывания.

## R7. Где живут роли персонажей и тексты промпта

**Decision**: все тексты промпта — общий префикс, персона каждого зверя и по 6 якорей на зверя —
лежат в **KV-конфиге службы** (ключ `config:prompts`), а не в коде Worker'а и не в клиентском
ассете. Предел длины реплики (`maxReplyLength`) живёт там же.

**Rationale**: FR-002 требует, чтобы роль не покидала службу, — иначе её достанут из APK и будут
дёргать Gemini чужим ключом с произвольным промптом. FR-002a добавляет второе требование, которого
не было в версии 0.2 документа: правка формулировки не должна требовать **ни релиза приложения, ни
редеплоя службы**. Формулировки промпта — самое часто правимое место во всей фиче (весь §4.2
архитектурного документа — это список правок, каждая из которых выбита сломанным прогоном), и
ставить между правкой и эффектом развёртывание значит правок не делать.

`characters.json` остаётся источником только визуальных данных и заготовленных реплик. Дублирования
не возникает: у клиента и у службы разные поля об одном персонаже, общий у них только `id`.

**Владелец `maxReplyLength`** (открытый вопрос 7 архитектурного документа) — конфиг службы. Предел
объявляется модели в промпте и применяется службой при обрезке, поэтому он должен лежать рядом с
промптом. Поле в `characters.json` остаётся ограничением на стороне отображения и в `/react` не
передаётся; расхождение безопасно в одну сторону — служба режет строже, чем показывает клиент.

**Названное следствие**: добавление стретч-персонажа (ленивец, попугай) требует правки ассета
приложения **и** правки конфига службы — но не её развёртывания. До 007 хватало одного ассета.

**Alternatives considered**: промпты в `personas.ts` (решение версии 0.2 этого файла) — отвергнуто
после v0.3: код означает редеплой на каждую правку формулировки. Клиент присылает `systemPrompt` —
отвергнуто, прямое нарушение FR-002. Убрать `maxReplyLength` из `characters.json` совсем —
отвергнуто: `CharacterCatalog` валидирует его при разборе ассета, и снятие поля тянет правку
разбора и его тестов ради устранения безвредного расхождения.

## R8. Порядок проверок и атомарность счётчиков

**Decision**: порядок обработки запроса — (1) разбор и валидация формы запроса (локально),
(2) kill switch из KV, (3) проверка подтверждения подлинности, (4) персональный счётчик,
(5) общий счётчик **выбранной модели**, (6) вызов Gemini. Инкремент с проверкой — один запрос на таблицу:
`INSERT ... ON CONFLICT(day, install_id) DO UPDATE SET count = count + 1 RETURNING count`.

**Rationale**: FR-016 задаёт «kill switch → персональный → общий → провайдер»; открытым оставался
только вопрос, где стоит проверка подлинности. Она стоит **до** счётчиков, потому что счётчики
ключуются по `installId`, который приходит от клиента и до проверки подлинности является
недоверенным вводом. Если пустить непроверенный запрос к счётчикам, атакующий с фальшивыми
`installId` не упрётся в персональный лимит (он их ротирует), но исчерпает **общий** — то есть
отключит AI всем настоящим пользователям одной строчкой в цикле. Обратный размен (расход квоты
Google на декодирование фальшивых токенов) заметно дешевле отказа в обслуживании.

Общий счётчик ключуется парой «сутки + модель» (`backend-proxy.md` §6.3): квоты Gemini считаются по
моделям отдельно, и без раздельного учёта служба не может понять, что основная модель исчерпана, а
резервная свободна, — переключение по R19 просто не заработает.

`RETURNING` отдаёт значение уже после инкремента, а D1 однопоточен на запись — поэтому обёртка
транзакцией не нужна, и два одновременных запроса с одного устройства получают разные значения
счётчика (FR-013).

**Alternatives considered**: счётчики до проверки подлинности (дешевле по квоте Google) — отвергнуто
по причине выше. Хранение счётчиков в KV — отвергнуто в `backend-proxy.md` §3.2: 1000 записей в
сутки и eventual consistency ломают обе половины требования. Durable Objects — YAGNI для суточных
счётчиков.

## R9. Ключ суток и граница дня

**Decision**: ключ — дата в UTC (`yyyy-mm-dd`), вычисляется **один раз** в начале обработки запроса
и переиспользуется для обоих счётчиков.

**Rationale**: закрывает краевой случай «смена суток во время обработки»: оба инкремента попадают в
одни сутки, двойного учёта нет. UTC — чтобы поведение не зависело от часового пояса конкретного
изолята. Это тот же принцип, что конституция IV предписывает клиенту (`AppClock`): время
запрашивается один раз и передаётся дальше значением, а не запрашивается повторно.

**Alternatives considered**: локальная дата пользователя — отвергнута: клиент может её подделать, и
лимит перестаёт быть лимитом.

## R10. Очистка счётчиков

**Decision**: Cron Trigger Worker'а раз в сутки — `DELETE FROM rate_limits WHERE day < ?` и то же
для `global_limits`, порог — сегодня минус 7 суток (Assumptions спеки).

**Rationale**: в D1 нет TTL-политики (открытый вопрос 2 в `backend-proxy.md`), иначе таблицы растут
неограниченно. 7 суток — запас на разбор инцидента при отсутствии собственного журнала
диагностики (Clarifications Q3).

**Alternatives considered**: удалять при каждом запросе — отвергнуто: лишняя запись в горячем пути
ради задачи, у которой нет требований к срочности.

## R11. Разделение отладочного и продового контуров

**Decision**: два окружения Wrangler в одном `wrangler.toml` — `[env.dev]` и `[env.production]`, у
каждого свои привязки D1/KV и свой набор секретов. Послабление проверки подлинности — переменная
`ALLOW_UNVERIFIED_INTEGRITY`, объявленная **только** в блоке `[env.dev]`; код читает её как
«отсутствует = выключено» и дополнительно требует `ENVIRONMENT === "dev"`. Тест проверяет, что
разобранный продовый конфиг не содержит этой переменной.

**Rationale**: FR-031 требует, чтобы послабление было *недоступно* в проде, а не выключено
переключателем. Раздельные окружения дают это на уровне конфигурации, двойное условие в коде — на
уровне рантайма, тест на конфиг — на уровне ревью. Три независимых слоя, потому что цена ошибки
здесь — открытый прокси.

**Alternatives considered**: один Worker с флагом — прямо отвергнут `backend-proxy.md` §11. Отдельный
файл конфигурации для dev — отвергнуто: два файла расходятся молча, `[env.*]` в одном файле
расходятся заметно.

## R12. Новые коды отказов на клиенте

**Decision**: `AiProxyFailure` получает два новых кода и один переименованный:

| Ответ службы | Код `AiProxyFailure` | Строка l10n |
|---|---|---|
| `429` + `scope: "device"` | `rateLimitedDevice` (значение `rate_limited_device`) | `tableAiRateLimitedError` (существующая) |
| `429` + `scope: "global"` | `rateLimitedGlobal` | `tableAiRateLimitedGlobalError` (новая) |
| `403` + `error: "integrity_failed"` | `integrityRejected` | `tableAiUnavailableError` (новая) |

`429` без разбираемого `scope` трактуется как `rateLimitedDevice` — более щадящая для пользователя
трактовка и не требующая от него ничего, кроме подождать.

**Rationale**: FR-023 требует различимых сообщений; текущий единственный `rate_limited` их не даёт.
`403` не может маппиться в `invalidResponse`, иначе пользователь увидит заготовленную реплику
персонажа вместо объяснения, почему AI не работает, — то есть отказ станет невидимым.

**Alternatives considered**: один код `rateLimited` + поле `scope` внутри `AppFailure` — отвергнуто:
`AppFailure` в этом проекте различает ситуации кодом, и `localizedMessage` — это `switch` по коду;
добавлять параллельный механизм ради одного случая означает две схемы вместо одной (DRY, конституция II).

## R13. Куда встраивается токен на клиенте

**Decision**: `DioAiProxyClient` получает зависимость `IntegrityTokenProvider` и сам добавляет
`integrityToken` в тело запроса. Сигнатура `AiProxyClient.react(...)` **не меняется**;
`AiReactionRepositoryImpl` не узнаёт о подтверждении подлинности ничего. Повтор по FR-010a
(«отклонили → обнови токен → повтори один раз») живёт внутри `DioAiProxyClient`.

**Rationale**: подтверждение подлинности — свойство транспорта, а не бизнес-операции «запросить
реакцию»; в `data/` и `domain/` ему делать нечего (принцип I). Побочная выгода — контракт
`specs/004-table-screen/contracts/ai-proxy-client.md` §5 остаётся в силе дословно, а диффом в
репозитории оказывается один новый файл в `core/` и один изменённый, а не переписанная цепочка
слоёв.

Общий бюджет 15 с (`AppConstants.aiRequestTimeout`) переезжает так, чтобы оборачивать **всю**
операцию вместе с повтором, а не каждую попытку по отдельности, — иначе FR-010a удваивает
максимальное ожидание пользователя до 30 с в нарушение SC-002.

**Alternatives considered**: репозиторий получает токен и передаёт параметром — отвергнуто: тянет
платформенную деталь в `data/` и меняет контракт 004. Отдельный `Dio`-интерсептор — отвергнуто:
интерсептор не умеет естественно выразить «повторить ровно один раз после обновления токена» без
скрытого состояния, а вся логика всё равно нужна только на одном эндпоинте.

## R14. Поведение вне Android

**Decision**: `IntegrityTokenProvider` на не-Android платформах возвращает `null`; клиент отправляет
запрос без поля `integrityToken`. Отладочный контур такой запрос принимает, продовый отклоняет
`403` → пользователь видит `tableAiUnavailableError`.

**Rationale**: приложение публикуется только под Android (конституция, «Технологические
ограничения»), а собираться обязано и под iOS. Падать или прятать кнопку на iOS — хуже, чем честный
отказ в одной функции: остальные экраны работают полностью. App Attest — явный TODO вне скоупа
(`backend-proxy.md` §9).

**Alternatives considered**: заглушка-токен на iOS — отвергнута: это ровно тот обход, ради закрытия
которого проверка и существует.

## R15. Сборка промпта, гвардрейлы и якоря

**Decision**: промпт склеивается из трёх частей — общий префикс + персона + **якорь** (образ для
сравнения). У каждого персонажа 6 якорей, выбор детерминированный:
`anchors[(dayOfYear + attempt) % anchors.length]`. Служба дополнительно жёстко обрезает ответ по
границе слова, если модель превысила предел длины.

**Rationale**: без ротации образов модель залипает на одном сравнении — замерено 12 прогонов на 4
разных моделях, и во всех 12 бегемот говорил про реку (`backend-proxy.md` §4.2). Это свойство
промпта, а не модели: смена модели не помогает вообще, помогает явный образ на каждый запрос.

Отсюда **бесплатно следует FR-018 фазы 004** («повторный тап MUST запрашивать новый вариант
ответа»): повторный тап увеличивает `attempt`, берётся следующий якорь, новая реплика гарантированно
про другое. Раньше это требование держалось на надежде, что сэмплирование даст другой текст, —
теперь оно обеспечено конструктивно. За один день образ у персонажа не повторится, пока не
исчерпаны все шесть.

Правила общего префикса, каждое из которых лечит подтверждённый на прогонах тик, а не
гипотетический: не начинать с обращения («друг мой» было в большинстве реплик всех персонажей); не
обещать, что завтра будет лучше (пёс обещал в 3 прогонах из 3); сравнения из живой природы, не из
техники (крокодил ушёл в шестерёнки и часовой механизм); не задавать вопросов; не пересказывать и не
цитировать ввод; ≤ `maxReplyLength`, язык пользователя; в тяжёлых темах манера отходит на второй
план. Отдельная формулировка, которая реально выбивает залипание: «не подменяй якорь теми образами,
которые кажутся тебе самыми очевидными для твоего вида: они уже были».

**Ловушка при написании якорей**: формулировки проверять на двусмысленность. Два реальных случая —
«часы без единого движения» модель прочла как настенные часы (имелась в виду длительность), а «на
глубине» вернуло бегемота в воду, от которой уходили. Оба раза виноват текст якоря, а не модель:
при странной реплике сначала перечитать якорь.

**Alternatives considered**: поднимать разнообразие температурой — отвергнуто, у моделей 3.x это
путь к зацикливаниям (R6). Случайный выбор якоря — отвергнут: недетерминированный, невоспроизводимый
в тестах и не гарантирует, что повторный тап даст **другой** якорь. Обрезка ровно по символу —
отвергнута, даёт обрыв на полуслове (FR-006).

## R16. Валидация ответа модели

**Decision**: ручной валидатор на ~30 строк в `proxy/src/gemini.ts`, без библиотеки схем. Проверяет:
`finishReason == STOP`; `mood` входит в набор `ReactionTone`; `reply` непуста; `intensity` — число,
не `NaN`, приведено клампом к 0.0–1.0. `character` не валидируется, а подставляется из запроса.

**Rationale**: проверяются три поля с простыми правилами, полностью совпадающими с §3 клиентского
контракта. Тянуть зависимость в Worker ради этого — против YAGNI и против бюджета размера бандла.

**Alternatives considered**: `zod` — отвергнут по причине выше; вернуться к нему стоит, если полей
станет заметно больше.

## R17. Домен службы

**Decision**: поддомен `*.workers.dev` в v1 (закрывает открытый вопрос 4 в `backend-proxy.md`).

**Rationale**: на функциональность не влияет, бесплатен, не требует настройки DNS. Свой домен —
косметика, которую можно добавить в любой момент сменой одного `--dart-define`.

**Alternatives considered**: свой домен сразу — отложено: работа есть, выгоды до релиза нет.

## R18. Чем покрываем тестами

**Decision**:

- **Служба** (Vitest + `@cloudflare/vitest-pool-workers`, эмулированные D1/KV, `fetch` к Google и
  Gemini подменяется): по одному контрактному тесту на каждый исход (`200`, `400`, `403`, `429
  device`, `429 global`, `503`, `422`), тест на атомарность (параллельные инкременты не дают
  превысить предел), тест на порядок проверок (при выключенном kill switch к Gemini не ходим), тест
  на обрезку длины, тест на то, что продовый конфиг не содержит послабления проверки подлинности.
  Добавлено после v0.3: ротация якорей (`attempt` 0..5 даёт шесть разных якорей, шестой запрос
  замыкает круг), переключение на резервную модель при исчерпанном счётчике основной и при `429` от
  Google, раздельность счётчиков по моделям, кламп `intensity` (включая `NaN` и значение `2`),
  отбраковка `mood` вне набора `ReactionTone`, `finishReason: MAX_TOKENS` → повтор → `422`,
  совпадение набора `mood` в схеме с enum клиента.
- **Клиент** (`flutter_test` + `mocktail`): кэширование токена в `IntegrityTokenProvider` (десять
  вызовов — одно обращение к платформе, SC-005a), повтор ровно один раз при `403` в
  `DioAiProxyClient` и отсутствие цикла при повторном `403`, маппинг новых кодов в
  `AiReactionRepositoryImpl`, отображение новых сообщений на экране «Стол». Добавлено после v0.3:
  `bloc_test` на счётчик попыток в `TableCubit` — растёт на настоящем ответе, **не** растёт на
  заготовленной реплике (R21), восстанавливается при загрузке экрана из сохранённых реакций дня.

**Rationale**: конституция VI требует покрытия нового кода и запрещает считать задачу выполненной с
падающими тестами; при этом новых Cubit-ов фича не добавляет, поэтому `bloc_test` здесь появляется
только там, где меняются уже существующие ветки `TableCubit`.

**Alternatives considered**: проверять службу только вручную по `quickstart.md` — отвергнуто: гонка
на счётчиках (FR-013) вручную не воспроизводится, а именно она защищает бюджет.

## R19. Переключение на резервную модель

**Decision**: список моделей по приоритету — из KV-конфига (`models`). Модель выбирается как первая
в списке, чей суточный счётчик не исчерпан. Если Gemini ответил `429` (выбит RPM), служба делает один
повтор с задержкой не более 2 секунд (FR-007b), затем берёт следующую модель списка, и только
если список исчерпан —
возвращает клиенту `422`. **Обе модели лежат в конфиге с первого развёртывания** (основная
`gemini-3.5-flash-lite`, резервная `gemini-3.1-flash-lite`): SC-006a требует переключения «без
вмешательства человека», а список из одной модели потребовал бы ручной правки конфига ровно в
момент отказа.

**Rationale**: `backend-proxy.md` §6.4 разводит два принципиально разных `429`. Свой счётчик — это
«ты сегодня уже наспрашивался, приходи завтра»; выбитый RPM провайдера (15 запросов в минуту на всех
пользователей сразу) — это «подожди пятнадцать секунд». Четверо пользователей, синхронно тапнувших
по четырём зверям, пробивают RPM — и показать им «твой дневной лимит исчерпан» было бы прямой
неправдой. Раздельный учёт по моделям (R8) — то, что делает переключение возможным.

**Alternatives considered**: доводить `429` провайдера до клиента как `rate_limited` — отвергнуто,
неверное сообщение пользователю. Round-robin — отвергнут в R6. Экспоненциальный backoff с
несколькими повторами — отвергнут: не укладывается в клиентский бюджет 15 секунд.

## R20. Откуда клиент берёт номер попытки

**Decision**: `TableCubit` держит `Map<String, int>` — число уже полученных сегодня реплик по каждому
персонажу. Заполняется при загрузке экрана из тех же реакций, которые он уже читает через
`DiaryRepository.reactionsFor(entryId)`, и увеличивается после каждой успешной реакции. Значение
передаётся в `AiReactionRepository.requestReaction` вместе с `moodScore`.

**Rationale**: экран уже загружает все реакции дня и схлопывает их в «последняя по персонажу» —
посчитать заодно количество ничего не стоит. Дополнительного запроса к базе не появляется, новых
зависимостей тоже.

**Это меняет контракт 004**: `AiReactionRepository.requestReaction` и `AiProxyClient.react` получают
по два новых параметра (`moodScore`, `attempt`). В версии этого файла от 0.2 утверждалось, что оба
интерфейса остаются нетронутыми, — после v0.3 архитектурного документа это неверно, и
`specs/004-table-screen/contracts/ai-proxy-client.md` §2 и §5 нужно обновить в рамках этой фичи.

**Alternatives considered**: считать попытки в `AiReactionRepositoryImpl`, запрашивая реакции у
`DiaryRepository`, — отвергнуто: лишний запрос к базе на каждый тап и зависимость репозитория от
репозитория, которой в проекте нигде больше нет. Отдельная колонка-счётчик в Drift — отвергнута:
данные уже есть в `character_reactions`, второй источник той же правды (DRY).

## R21. Заготовленные реплики и `attempt`

**Decision**: заготовленная (fallback) реплика **не увеличивает** номер попытки — счётчик растёт
только на настоящих ответах AI.

**Rationale**: `attempt` существует ради выбора якоря. Если отказ AI сдвинет счётчик, следующий
настоящий тап перескочит через якорь, и пользователь не увидит образ, который должен был получить.
Заготовленная реплика при этом всё равно сохраняется в дневник (FR-021 фазы 004) — сдвигается только
счётчик попыток, а не история.

**Alternatives considered**: считать любую сохранённую реакцию попыткой — отвергнуто по причине
выше; это дало бы «пропуски» в ротации образов ровно у тех пользователей, у кого AI и так отказывал.
