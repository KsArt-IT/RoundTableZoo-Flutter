# Feature Specification: Экран «Дневник»

**Feature Branch**: `005-diary-screen`

**Created**: 2026-08-19

**Status**: Draft

**Input**: User description: "Diary screen"

## User Scenarios & Testing *(mandatory)*

Экран «Дневник» — вторая вкладка приложения. Сегодня на её месте заглушка. Стол (фаза 004) уже
пишет записи дня и реакции персонажей в хранилище; Дневник — первый экран, который эти данные
читает и показывает пользователю в ретроспективе: список дней, график настроения, реплики зверей за
каждый день и экспорт истории.

### User Story 1 — Просмотреть историю настроения (Priority: P1)

Пользователь открывает вкладку «Дневник» и видит список прошлых дней в обратном хронологическом
порядке: дата, эмодзи настроения и текст дня, если он был. Список работает офлайн — все данные уже
на устройстве.

**Why this priority**: это и есть смысл вкладки — без списка дней «Дневник» не существует. Строится
поверх уже готового хранилища (фазы 001–004), новых данных не требует.

**Independent Test**: отметить настроение за несколько дней через Стол → открыть Дневник в
авиарежиме → увидеть все дни списком, самый новый — сверху.

**Acceptance Scenarios**:

1. **Given** за последние дни есть отметки настроения, **When** пользователь открывает Дневник,
   **Then** список показывает каждый день — дату, эмодзи настроения и текст (если был) — от нового
   к старому.
2. **Given** записей ещё нет, **When** пользователь открывает Дневник, **Then** показано явное
   пустое состояние, а не пустой экран без объяснения.
3. **Given** устройство офлайн, **When** пользователь открывает Дневник, **Then** список полностью
   отображается без сетевых ошибок и без зависшего индикатора загрузки.
4. **Given** у дня есть только настроение без текста, **When** день показан в списке, **Then** он
   отображается корректно, без «сломанного» пустого поля текста.
5. **Given** пользователь отмечает настроение на Столе, пока вкладка Дневника открыта в фоне,
   **When** он переключается на Дневник, **Then** новая запись видна без перезапуска приложения.
6. **Given** история длиннее одной подгружаемой страницы, **When** пользователь докручивает список
   до конца, **Then** подгружаются более старые дни без потери уже показанных и без дублей.
7. **Given** все дни истории уже подгружены, **When** пользователь докручивает список до конца,
   **Then** экран явно показывает, что дальше дней нет, а не бесконечный индикатор загрузки.

### User Story 2 — Видеть тренд настроения на графике (Priority: P2)

Над списком (или рядом с ним) показан график: та же история дней, но как визуальный тренд
настроения по датам.

**Why this priority**: даёт мгновенное считывание «как я себя чувствовал в последнее время» —
ценность поверх уже работающего списка (US1), не самостоятельная замена ему.

**Independent Test**: отметить настроение с разными значениями за несколько дней → открыть
Дневник → график показывает точку на каждый день, совпадающую со значением в списке.

**Acceptance Scenarios**:

1. **Given** несколько дней с разными оценками настроения, **When** график построен, **Then**
   каждая точка соответствует сохранённому `moodScore` этого дня.
2. **Given** внутри показанного диапазона есть день без записи, **When** график построен, **Then**
   этот день показан как пропуск, а не как конкретное значение настроения.
3. **Given** сохранён только один день истории, **When** график построен, **Then** он корректно
   показывает одну точку, не ломается и не выглядит пустым по ошибке.
4. **Given** у дня есть реакции персонажей с разным тоном, **When** график построен, **Then** тон и
   амплитуда реакций никак не влияют на положение точки — только `moodScore`.
5. **Given** история накопилась за много месяцев, **When** график построен, **Then** он остаётся
   читаемым и отзывчивым, не пытаясь отрисовать каждый день по отдельности без агрегации, если
   точек слишком много для одной точки на день (см. Assumptions).

### User Story 3 — Прочитать реплики зверей за день (Priority: P3)

Пользователь раскрывает день в списке и видит реплики персонажей, полученные в этот день —
включая все варианты, если зверя переспрашивали несколько раз.

**Why this priority**: возвращает эмоциональную ценность Стола в ретроспективе — заметная, но не
базовая часть экрана; список (US1) уже самостоятельно полезен без неё.

**Independent Test**: на Столе получить две реплики одного персонажа за день (переспросить) и одну
реплику другого → открыть Дневник → раскрыть этот день → увидеть все три реплики.

**Acceptance Scenarios**:

1. **Given** у дня есть реплики персонажей, **When** пользователь раскрывает день, **Then** каждая
   реплика показана вместе с именем персонажа, которому принадлежит.
2. **Given** один персонаж отвечал за день дважды, **When** день раскрыт, **Then** видны оба
   варианта, а не только последний.
3. **Given** реплика — заготовленная (`isFallback`), **When** она показана, **Then** она визуально
   отличима от настоящего ответа AI тем же способом, что и на Столе (иконка, не только цвет).
4. **Given** у дня нет реплик персонажей, **When** день раскрыт, **Then** показано явное «реплик не
   было», а не пустой блок, похожий на ошибку.
5. **Given** пользователь только что открыл Дневник, **When** список показан, **Then** ни один день
   не раскрыт заранее — раскрытие только по действию пользователя.
6. **Given** один день уже раскрыт, **When** пользователь раскрывает другой день, **Then** первый
   день остаётся раскрытым — оба дня показывают реплики одновременно.

---

### User Story 4 — Экспортировать историю (Priority: P4)

Пользователь нажимает «экспорт» и получает файл истории в формате CSV через системный диалог
«поделиться».

**Why this priority**: приятное дополнение для переноса данных вовне; наименее критичная часть
экрана и естественная надстройка над уже показанным списком.

**Independent Test**: при наличии истории нажать «экспорт» → открывается системный диалог
«поделиться» с CSV-содержимым, в котором корректные данные.

**Acceptance Scenarios**:

1. **Given** история не пуста, **When** пользователь нажимает «экспорт», **Then** открывается
   системный диалог «поделиться» с CSV-файлом.
2. **Given** CSV открыт/проверен, **Then** столбцы строго `date, moodScore, dayText, characterId,
   characterReply` — по одной строке на реплику персонажа; день без реплик даёт одну строку с
   пустыми `characterId`/`characterReply`.
3. **Given** истории ещё нет, **When** пользователь смотрит на экран, **Then** действие «экспорт»
   недоступно (не создаёт пустой или сломанный файл).
4. **Given** устройство офлайн, **When** пользователь экспортирует, **Then** экспорт всё равно
   срабатывает — сетевого запроса не требуется.

---

### Edge Cases

- Пользователь докручивает список быстрее, чем успевает подгрузиться следующая страница: повторный
  запрос той же страницы не создаёт дублей и не сбивает порядок уже показанных дней.
- История пуста при первом использовании (ни одного дня ещё не записано на Столе): пустое состояние
  показывается сразу, без ложной попытки подгрузки несуществующей первой страницы.
- Очень большая история (сотни/тысячи дней): подгрузка следующих страниц и построение графика не
  замораживают интерфейс и не приводят к паузам, читаемым как «зависло».
- Вычисленный день, в который после смены часового пояса или «часа начала дня» попали две записи:
  и список, и график показывают только самую позднюю по времени запись — то же правило, что и на
  Столе.
- Хранилище в режиме «только чтение» (после восстановления без сохранения): Дневник MUST NOT
  показывать «истории пока нет» как будто это правда — пользователь должен понимать, что причина в
  недоступности хранилища, а не в отсутствии записей.
- Очень длинный текст дня в списке: в свёрнутой карточке обрезается, полностью показывается тем же
  раскрытием карточки, что и реплики (одно действие, не два — Clarifications, session 2026-08-19,
  checklist review), и не ломает вёрстку.
- Увеличенный системный масштаб шрифта: карточка дня остаётся читаемой и не обрезает управляющие
  элементы (проверяется тем же способом, что и другие экраны, — `TextScaler.linear(2)`).
- Текст дня или реплика содержит запятую, кавычку или перенос строки: CSV-экспорт экранирует их
  корректно, а не портит структуру файла.
- Персонаж, чья реплика сохранена, был позже выключен или удалён из настроек: реплика всё равно
  показывается в Дневнике (по сохранённому `characterId`), не пропадает и не ломает экран.
- Смена языка или темы, пока Дневник открыт: уже показанные данные остаются на месте, интерфейс
  просто перестраивается в новой локали/теме.

## Clarifications

### Session 2026-08-19

- Q: Дневник показывает полную историю без ограничения или скользящее окно (например, последние 30
  дней), как допускает MVP-упрощение в `04-requirements-diary.md`? → A: Полная история без
  ограничения окна — список подгружается постранично (бесконечный скролл), экспорт CSV покрывает
  всю сохранённую историю.
- Q: Может ли быть раскрыто несколько дней одновременно, или раскрытие одного дня сворачивает
  предыдущий раскрытый (аккордеон)? → A: Несколько одновременно — раскрытие каждого дня независимо,
  не аккордеон.
- Q: Нужен ли графику настроения отдельное Semantics-описание для чтения экрана (например, сводка
  «тренд растёт/падает»), или достаточно того, что те же данные уже доступны через список дней под
  графиком? → A: График декоративен для программ чтения с экрана — те же данные (moodScore по дням)
  уже доступны текстово через список; отдельная сводка тренда не требуется.
- Q: Если чтение из хранилища завершается непредвиденной ошибкой (не режим «только чтение», а,
  например, повреждённая БД), что должен показать Дневник? → A: Общий баннер ошибки, отличимый и от
  пустого состояния, и от readonly-баннера, с возможностью повторить попытку — та же практика, что
  на других экранах приложения.
- Q: График настроения всегда показывает всю историю целиком на экране (статичный, без
  скролла/зума), или пользователь должен иметь возможность листать/масштабировать его? → A: С
  горизонтальным скроллом/зумом — пользователь может рассмотреть конкретный период ближе, а не
  только видеть всю историю сразу агрегированной.

### Session 2026-08-19 (checklist review, `checklists/diary.md`)

Ответы на пробелы, найденные проверкой качества требований. Каждый закрывает конкретный пункт
чек-листа.

- Q (CHK035): текст дня и реплики раскрываются одним действием или двумя? → A: **одним** — тап по
  карточке раскрывает и полный текст дня, и блок реплик; один тап-таргет, одно состояние
  «раскрыто/свёрнуто» для программ чтения с экрана.
- Q (CHK021): какой диапазон график показывает при открытии? → A: **последние 30 дней** (дневная
  гранулярность, правый край — самый свежий день); вся история доступна отдалением. Диапазон
  совпадает с первой страницей списка, поэтому график и видимая часть списка показывают одно и то же.
- Q (CHK010): в каком виде выводится дата в карточке дня? → A: **локальный формат даты**
  (`DateFormat.yMMMMd` текущей локали), без «Сегодня/Вчера» — исключает расхождение подписи с
  вычисленным днём при полуночном ролловере.
- Q (CHK033): нужно ли предупреждение перед CSV-экспортом? → A: **нет** — экспорт инициирует сам
  пользователь и сам выбирает получателя в системном диалоге; раскрытия требует только отправка
  текста внешнему AI (конституция §V), а не локальный шаринг по явному действию.
- Q (CHK002, CHK003): когда стартует подгрузка следующей страницы? → A: когда до конца уже
  показанного списка остаётся меньше половины страницы; от этого момента отсчитывается SC-008.
- Q (CHK006): что происходит при ошибке подгрузки **следующей** страницы? → A: уже показанные дни
  остаются на месте, в конце списка появляется строка с ошибкой и повтором; экран не переходит в
  состояние ошибки целиком (в отличие от FR-008a, который про первую загрузку).
- Q (CHK022): диапазон оси значений графика? → A: **фиксированный 1–5** — подстройка под данные
  преувеличивала бы амплитуду и расходилась бы со шкалой из списка.
- Q (CHK030): как выглядит недоступный экспорт? → A: кнопка **видна и заблокирована** (не скрыта),
  с подписью для программ чтения с экрана — иначе действие невозможно обнаружить.
- Q (CHK032): что при отмене системного диалога «поделиться»? → A: не ошибка — экран возвращается в
  обычное состояние молча.
- Q (CHK013): что при повторной неудаче «повторить»? → A: тот же баннер ошибки, без счётчика попыток
  и без экспоненциальной задержки.

## Requirements *(mandatory)*

### Functional Requirements

**Список дней**

- **FR-001**: Дневник MUST показывать список дней с сохранённой записью настроения в обратном
  хронологическом порядке (самый новый — первым), включая дату, эмодзи настроения (по той же шкале,
  что и на Столе — `core/constants/mood_scale.dart`, повторно, не новый маппинг) и текст дня, если
  он был.
- **FR-002**: Дневник MUST читать записи из того же хранилища, что пишет Стол (`day_entries`,
  `character_reactions`), и MUST NOT вести отдельную копию данных.
- **FR-003**: Список и график MUST полностью работать офлайн — без обращения к сети.
- **FR-004**: Дневник MUST в итоге показывать полную историю без ограничения по времени; список
  MUST подгружаться постранично (например, «бесконечный скролл») — не единым запросом всех дней
  сразу (Clarifications, session 2026-08-19).
- **FR-004a**: Подгрузка следующей страницы MUST начинаться по приближению пользователя к концу уже
  показанного списка и MUST NOT требовать отдельного тапа «загрузить ещё» как единственного способа
  (тап-кнопка допустима как fallback, если подгрузка по прокрутке недоступна).
- **FR-004b**: Повторная или параллельная подгрузка одной и той же страницы MUST NOT создавать
  дублирующиеся дни в списке.
- **FR-004c**: Когда все дни истории уже подгружены, список MUST явно показать это состояние
  («дальше дней нет»), а не бесконечный индикатор загрузки.
- **FR-005**: День с отметкой настроения, но без текста и без реплик персонажей, MUST отображаться
  в списке корректно — без текста-заглушки, читаемого как ошибка.
- **FR-006**: Если вычисленный день содержит несколько записей (после смены часового пояса или
  «часа начала дня»), список и график MUST показывать только самую позднюю по `occurredAt`.
- **FR-007**: При отсутствии сохранённых дней в истории Дневник MUST показывать явное пустое
  состояние, отличимое от состояния загрузки и от режима «только чтение» (см. FR-029).
- **FR-008**: Пока данные первой страницы загружаются, экран MUST показывать состояние загрузки, а
  не пустой список, читаемый как «истории нет».
- **FR-008a**: При непредвиденной ошибке чтения из хранилища (не режим «только чтение» — например,
  повреждённые данные) Дневник MUST показать баннер ошибки, отличимый от пустого состояния (FR-007)
  и от readonly-баннера (FR-029), с возможностью повторить попытку загрузки (Clarifications, session
  2026-08-19).
- **FR-009**: Дневник MUST отражать запись, только что сохранённую на Столе, без необходимости
  перезапускать приложение, если вкладка Дневника остаётся открытой в фоне.

**График**

- **FR-010**: Дневник MUST показывать график настроения по датам, построенный по той же полной
  истории, что и список (FR-004) — без искусственного ограничения диапазона дат.
- **FR-010a**: При объёме истории, для которого одна точка на каждый день перегружает график, MUST
  использоваться агрегация по более крупному периоду (неделя/месяц) вместо построчного вывода
  каждого дня — график MUST оставаться читаемым при любом объёме накопленной истории.
- **FR-010b**: График MUST поддерживать горизонтальный скролл/масштабирование, чтобы пользователь мог
  рассмотреть конкретный период ближе (например, отдельный месяц по дням), а не только видеть всю
  историю сразу в агрегированном виде (Clarifications, session 2026-08-19).
- **FR-011**: График MUST строиться исключительно по `day_entries.moodScore`; тон и амплитуда
  реакций персонажей (`character_reactions.tone`/`intensity`) MUST NOT влиять на график.
- **FR-012**: День (или, при агрегации по FR-010a, период) без сохранённой записи MUST визуально
  отличаться на графике от дня/периода с явно сохранённым значением настроения — пропуск не может
  читаться как конкретная оценка.
- **FR-013**: График MUST оставаться корректным и читаемым при малом числе точек (включая ровно
  одну) — без падения и без вводящего в заблуждение пустого вида.
- **FR-013a**: График для программ чтения с экрана MUST считаться декоративным элементом (не
  озвучивать сводку тренда) — те же значения `moodScore` по дням уже доступны текстово через список
  дней под графиком, отдельного Semantics-описания графика не требуется (Clarifications, session
  2026-08-19).

**Реплики персонажей за день**

- **FR-014**: Каждый день в списке MUST иметь возможность раскрыть реплики персонажей за этот день;
  по умолчанию реплики свёрнуты. Раскрытое/свёрнутое состояние каждого дня MUST быть независимым —
  раскрытие одного дня MUST NOT сворачивать ранее раскрытые дни (не аккордеон, несколько дней могут
  быть раскрыты одновременно; Clarifications, session 2026-08-19).
- **FR-015**: Раскрытые реплики MUST показывать все сохранённые варианты дня для каждого персонажа
  (включая все переспросы), а не только последний, — в отличие от Стола, который показывает только
  последнюю реакцию персонажа.
- **FR-016**: Каждая показанная реплика MUST быть подписана именем персонажа, которому принадлежит.
- **FR-017**: Заготовленная реплика (`isFallback: true`) MUST быть визуально отличима от настоящего
  ответа AI тем же способом, что и на Столе (иконка/форма, не только цвет — FR-027c фазы 004), и в
  описании для программ чтения с экрана.
- **FR-018**: День без реплик персонажей при раскрытии MUST показывать явное «реплик не было», а не
  пустой блок.
- **FR-019**: Если `characterId` сохранённой реплики отсутствует в текущем конфиге персонажей
  (персонаж удалён/переименован из ассета), реплика MUST всё равно отображаться, не ломая экран.

**Экспорт CSV**

- **FR-020**: Дневник MUST предоставлять действие «экспорт», формирующее CSV-файл истории и
  открывающее системный диалог «поделиться» через тот же `ShareService`, что и шаринг реплики на
  Столе (переиспользование, не второй механизм).
- **FR-021**: Столбцы CSV MUST быть строго `date, moodScore, dayText, characterId, characterReply` —
  одна строка на реплику персонажа; день без реплик MUST давать одну строку с пустыми
  `characterId`/`characterReply`.
- **FR-022**: Экспортированное значение `date` MUST быть вычисленным днём записи (тем же, что
  использует список и график), а не сырой сохранённой отметкой времени.
- **FR-023**: Экспорт MUST охватывать полную сохранённую историю целиком, а не только уже
  подгруженные на экране страницы списка (FR-004).
- **FR-024**: Действие «экспорт» MUST быть недоступно (не запускать создание пустого/сломанного
  файла), когда в истории нет ни одной записи.
- **FR-025**: Экспорт MUST NOT требовать сетевого соединения.
- **FR-026**: Значения CSV, содержащие запятую, кавычку или перенос строки, MUST быть корректно
  экранированы — файл MUST оставаться валидным CSV.

**Общие**

- **FR-027**: Дневник MUST быть read-only относительно данных Стола: экран MUST NOT предоставлять
  редактирование или удаление отметки настроения, текста дня или реплик персонажей — единственный
  писатель этих данных остаётся Стол.
- **FR-028**: Все строки экрана MUST быть локализованы (обязательный русский, структура для
  английского и украинского).
- **FR-029**: В режиме хранилища «только чтение» (после восстановления без сохранения) Дневник MUST
  показывать баннер режима (тот же, что уже рисует общий `ShellPage`) и MUST NOT интерпретировать
  недоступность хранилища как «записей нет» (см. Edge Cases).
- **FR-030**: Тап-таргет каждой иконочной кнопки экрана (включая «раскрыть» и «экспорт») MUST быть
  не меньше принятого в проекте минимума (48dp) и MUST иметь `Semantics`-подпись.

### Key Entities

- **Запись дня** и **Реакция персонажа**: те же сущности, что пишет Стол (фаза 004) — Дневник
  только читает их, новых полей не добавляет.
- **Точка графика настроения**: производная от записи дня величина для построения графика (день +
  `moodScore`) — отдельная от `Запись дня` модель на уровне реализации (не смешивать доменную
  сущность с моделью графика), содержательно она не добавляет данных сверх того, что уже есть в
  записи дня.
- **Строка CSV-экспорта**: `date`, `moodScore`, `dayText`, `characterId`, `characterReply` — прямое
  отображение записей дня и реакций персонажей в плоский построчный формат.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь видит первую страницу списка истории не позже 2 секунд после открытия
  вкладки Дневник при уже загруженном приложении, независимо от общего объёма накопленной истории.
- **SC-002**: 100% точек графика совпадают с сохранённым `moodScore` соответствующего дня —
  проверяется на наборе из 10 дней со смешанными оценками.
- **SC-003**: Раскрытие дня с репликами персонажей срабатывает без ошибок в 100% случаев и
  показывает все сохранённые варианты, включая переспросы того же персонажа.
- **SC-004**: Список, график и раскрытие реплик работают со 100% успехом при полностью отключённой
  сети (10 попыток из 10).
- **SC-005**: Экспорт CSV открывает системный диалог «поделиться» не позже 3 секунд после нажатия
  для года ежедневной истории с репликами персонажей (≈365 дней, несколько реплик в день) — без
  зависания интерфейса даже при большем объёме.
- **SC-006**: Автоматическая проверка доступности не находит на экране элементов управления без
  текстовой метки и с тап-таргетом меньше 48dp.
- **SC-007**: Ни один экспортированный или показанный на экране день не отражает значение
  настроения, отличное от сохранённого `moodScore` этого дня — данные графика/списка/CSV никогда не
  выводятся из тона реакций персонажей.
- **SC-008**: Докрутка списка до конца текущей страницы даёт следующую страницу не позже 1 секунды
  после срабатывания подгрузки, без дублей и без потери уже показанных дней (10 подгрузок подряд из
  10 без дублей).

## Assumptions

- **Готовое основание.** Хранилище записей дня и реакций (`DiaryRepository`), маппинг эмодзи/цвета
  настроения (`core/constants/mood_scale.dart`), `ShareService` и локализация уже реализованы
  фазами 001–004 и переиспользуются как есть; новые таблицы БД не заводятся.
- **Полная история, постраничная подгрузка.** Решение зафиксировано в Clarifications. Первоначальное
  допущение, что подгрузка ляжет на существующий `DiaryRepository.entriesBetween` сдвигом границы
  `from` без новых методов, **не подтвердилось** при планировании: у диапазонного запроса нет ответа
  на вопрос «есть ли записи старее», поэтому FR-004c недостижим, а при разрыве в истории одна
  страница вырождается в серию пустых запросов вопреки SC-008. Контракт репозитория дополняется
  методами чтения (`plan.md` §Complexity Tracking, `research.md` R2/R3/R11); существующие методы и
  их семантика не меняются.
- **Без редактирования и удаления.** Экран только читает; изменение/удаление отметки настроения,
  текста или реплик персонажей из Дневника не предусмотрено — при необходимости это отдельная
  функциональность, не часть этого среза.
- **Агрегация графика — по объёму, не всегда по дням.** При небольшой истории график показывает
  каждый день отдельной точкой; порог, после которого включается недельная/месячная агрегация
  (`architecture-full.md`), — деталь реализации, а не часть этой спеки, значимо для FR-010a только
  то, что график не перестаёт быть читаемым при любом объёме данных.
- **Раскрытие дня — не экран Стола.** Просмотр реплик за день — инлайн-раскрытие карточки в списке,
  не переход на отдельный интерактивный экран (`04-requirements-diary.md`: «не обязательно
  интерактивный стол»).

## Dependencies

- `DiaryRepository` (`entriesBetween`, `reactionsFor`, `watchEntriesChanged`) — уже реализован фазой
  001, методы используются как есть, без изменений контракта.
- `core/constants/mood_scale.dart` и `core/sharing/share_service.dart` — реализованы фазой 004,
  переиспользуются без дублирования логики.
- Статический конфиг персонажей (`CharacterCatalog`) — для отображения имени персонажа рядом с
  репликой; отсутствие персонажа в конфиге не должно ломать отображение (FR-019).

## Out of Scope

- Редактирование или удаление записи дня, текста дня или реплик персонажей из Дневника.
- Интерактивный «стол» при открытии конкретного дня — только просмотр.
- Фильтрация, поиск, сортировка или переход к конкретной дате в списке дней (только постраничная
  прокрутка от новых дней к старым).
- Дополнительные метрики на графике сверх `moodScore` (например, отдельная линия по тону реакций).
- Шаринг отдельной реплики персонажа из Дневника (уже есть на Столе, фаза 004 — не дублируется
  здесь).
- Экспорт в форматы, отличные от CSV.
